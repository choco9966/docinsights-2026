## 공통 제약

**실행 갱신:** 119건·973페이지의 source-only 입력을 고정했다. 기존 OCR이 일부 페이지만 포함한 9건은 누락을 표시하고 전체 PDF 이미지를 제공한다. 구조·수락·runner 회귀 검사 45개가 통과했고 별도 재검토 중이다. CLI Astra 경로는 호환 오류로 실패를 보존했다. 네이티브 Astra/ultra 합성 검사 통과 후 실제 첫 문항을 검토 중이며, 독립 수락 전에는 병렬 대량 검토를 시작하지 않는다. 진행의 최신 근거는 로컬 execution ledger와 문제별 수락 receipt다.

- 정확도 우선, 비용 선측정, 고정 8시간 제한 없음.
- 이번 전체 범위는 held-out 1,730건. 심층 대상 119건 + 나머지 1,611건.
- 공식 질문·PDF만 정답 근거로 사용한다. Validation 문항별 reference와 피드백은 생성 입력에서 제외한다.

- 기존 승인본·producer·목표 상태를 소급 변경하지 않는다.

- 문항별 결과는 로컬 비공개 artifact로 유지한다. 공개 Git 문서에는 목표·절차·집계와 합성 회귀 예시만 남긴다.

- [x] 아래 산식으로 단일 요청 순차 환산, 실측 동시성 5 환산, 재검토 부하 시나리오를 보고했다. 유효 출력 처리량 검증은 단계 1a 이후 다시 필요하다.

시간 변수: 개별 요청 시간 `t_i`, 5건 평균 `mean_t`, 5건 동시 요청 전체 경과 `W5`, 페이지 준비 시간 `P5`. 의미 검토·후처리는 별도다.

```text
순차 모델 호출 환산 = 1730 × mean_t
5개씩 실행하는 wave 환산 = ceil(1730 / 5) × W5 = 346 × W5
페이지 준비 포함 단순 환산 = 346 × (W5 + P5)
전체 소요 = 준비/검사 구현 + 119건 Ultra 추가 판정 + Sol 전수 검토
          + 불일치 판정 + 통합/최종 검증
```

5건의 단일 wave는 전수 처리량의 보장이 아니다. 모델 대기·문서 길이·캐시·고난도 비율이 다르고 표본이 작으므로 통계적 95% 구간을 만들지 않는다. 추가 작업 0%·25%·50% 시나리오는 가정임을 밝힌다. 실제로 측정하지 않은 Ultra/medium/다른 동시성의 시간을 Sol/high 측정값으로 대체하지 않는다. 전수 실행 중 첫 25건과 100건에서 같은 식을 갱신한다.

표본의 attention 비율 2/5는 실제 119/1,730보다 높다. 추가로 `1611 × 목록 밖 평균 + 119 × attention 평균`을 순차 가중 환산으로 계산한다. 병렬 전망은 이 값에 실측 `W5 / sum(t_i)`를 곱한 작업량 시나리오로 제시한다. 각 그룹 표본이 3건·2건뿐이므로 가중 환산도 정확한 모집단 추정이나 보수적 상한이라고 부르지 않는다.

## 단계 1a — 전송·출력 계약 복구 후 유효 처리량 확인

첫 시험에서 모든 요청에 재접속 오류와 HTTPS fallback 오류 item이 남았다. 답에 부가 설명이 들어가거나 Evidence에 block ID 대신 문장이 들어왔다. schema가 문자열이면 모두 허용한 탓에 문장으로 적은 규칙이 강제되지 않았다. CLI 옵션 확인을 실제 전송 시험으로 대신한 Root의 사전 검사 누락도 수정한다.

- [ ] 현재 버전·옵션을 모델 호출 없이 확인하고, 기존 전송 실패 회고와 대조해 변경할 원인을 정한다. 동일 조건의 무한 재시도나 오류 무시로 해결하지 않는다.
- [ ] 단계 2의 최소 형식 검사를 먼저 구현한다. 답은 설명 없는 최종 표현만 허용하고, 단위·기호식 예외는 문항 요구로 명시한다. Evidence에는 원문에서 확인한 ID만 넣고 page 위치·설명은 별도 필드에 둔다. 모든 실제 ID가 `bNN`이라는 가정은 금지한다.
- [ ] 동일 전송 경로와 출력 계약으로 비대회 합성 1건을 실행한다. strict 완료, 검증 가능한 usage, top-level error·turn.failed·error item 0개, 저장된 출력과 일치하는 최종 메시지 1개를 요구한다.
- [ ] 합성 검사가 통과한 뒤 새 run ID로 실제 1건을 실행하고 실행·형식·source 연결 검토를 통과시킨다. 원본 5건은 실패 기록으로 보존한다.
- [ ] 이후 제한된 새 병렬 묶음에서 수락 건수당 토큰·시간과 실패 복구 비용을 측정한다. 최초 5건을 성공할 때까지 반복한 결과로 합치지 않는다.
- [ ] 입력 축소나 동적 작업 큐는 별도 변경으로 측정한다. 이번 시험은 전체 페이지 이미지를 한 요청에 넣었으므로, 필요한 페이지만 읽는 방식이나 빈 슬롯에 즉시 다음 작업을 넣는 방식의 절감률은 아직 알 수 없다. 원문 확인 범위·검토 품질을 줄여 속도를 얻지 않는다.

종료 조건은 오류가 없는 단일 요청을 넘어, 동일 계약의 실제 유효 처리량을 확보하는 것이다. 그전에는 전수 작업을 예약하지 않는다. 전송 수락 검사를 완화하거나 원시 응답을 자동 정규화해 성공 수를 늘리지 않는다.

## 단계 2 — 통합 오류를 막는 최소 수락 검사

담당: 구현 담당 1명, 별도 검토 1명, Root 승인. 대량 의미 판정 전에 완료한다. 5건 시험은 승인본을 수정하지 않는 격리된 진단이므로 이 구현에 앞서 가능하다.

예정 파일: 새 로컬 실행 디렉터리의 `tools/review_gate.py`, `tools/test_review_gate.py`, `contract.json`. 기존 동결 assembler를 수정하지 않는다. 코드로 일반화할 때에는 별도 개발 브랜치에서 필요한 부분만 저장소 모듈로 반영한다.

한 문제의 현재 결정은 `instance_id`, `input_revision_sha256`, `source_facts`, `target_candidates`, `selected_candidate_id`, `answer`, `evidence`, `solution`, `axes`, `assumptions`, `hold_reasons`, `review_bindings`로 구성한다. `review_bindings`에는 문제 ID·검토 대상 revision·필드·검토자·판정이 들어간다. 버전은 정규화 JSON의 SHA-256으로 만들며 source/answer/Evidence 변경 시 관련 승인을 무효화한다.

필수 인터페이스는 `validate_decision(decision, expected_id, expected_revision) -> list[str]`이다. 빈 목록만 구조 수락이다. `validate_transition(previous, proposed) -> list[str]`는 구버전 패치, 변경 범위, stale 승인을 검사한다. 내용의 타당성은 별도 독립 source review를 요구한다.

- [ ] 합성 사례로 먼저 실패 검사를 만든다: 답 `900`을 유지하며 풀이가 `3+4=7`만 지지하는 변경은 거부한다.
- [ ] 원문을 명확히 읽었다는 판정과 ‘읽을 수 없음’이라는 현재 이유의 충돌을 content-review 필요로 돌린다. 자유문장 전체의 의미를 정규식으로 확정하지 않는다.
